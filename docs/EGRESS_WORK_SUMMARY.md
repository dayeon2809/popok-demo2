사이트가 사진을 **원본 크기 그대로** 내보내고 있어서 무료 한도를 3배 넘겼다.
사진을 **자동으로 줄여 보내도록** 고쳤다.

## 무슨 일이 있었나

8월 11일, Supabase(사진과 데이터를 보관하는 외부 서비스)에서 경고가 왔다.

```
한 달 사용 가능: 5.5 GB
실제 사용:      16.41 GB   (3배 초과)
8월 14일 이후 서비스 제한
```

제한이 걸리면 사진이 안 뜨고, 데이터까지 막히면 사이트 전체가 멈춘다.
**Pro 요금제로 한 달 결제해 급한 불은 껐다.** 다음 달 무료로 되돌리는 것이 목표이고, 아래 작업은 그것을 위한 것이다.

---

## 왜 이런 일이 생겼나

### 1. 사진을 원본 그대로 보내고 있었다

화면에 보이는 아티스트 사진은 엄지손톱만 한데, 실제로 오가는 데이터는 원본 통째였다.

실제로 재본 수치다.

| | |
|---|---|
| 홈 화면이 쓰는 사진 | 185장 |
| 평균 크기 | 835 KB |
| 가장 큰 사진 | **5.8 MB** |

우표만 하게 보여줄 사진인데 매번 대형 포스터 원본을 보내고, 화면에서만 줄여 붙이고 있었던 셈이다.

### 2. 줄여주는 장치는 이미 있었다 — 일부에만 연결돼 있었을 뿐

8월 2일에 사진을 자동으로 줄이는 장치가 이미 만들어져 있었다. 성능도 확실했다.

```
5.8 MB 원본  →  장치 통과  →  23.7 KB     (245배 감소)
```

문제는 이 장치가 **전체 화면의 일부에만 연결**돼 있었다는 것이다. 나머지 화면은 여전히 원본을 내보냈다.

### 3. 캐시로는 해결되지 않는다

"캐시를 켜면 되지 않나" 싶지만 아니다. 요금은 **이용자에게 배달된 데이터의 양**으로 매겨진다. 5명이 보면 5번분이 나가고, 그건 캐시로 줄일 수 없다.

줄일 수 있는 건 **한 번에 나가는 크기**뿐이다. 그래서 아래 작업이 전부 "크기를 줄이는" 방향이다.

---

## 한 작업과 그 이유

### 작업 1. 공개 화면 26곳을 자동 축소 장치에 연결했다

**왜 했나 —** 원인의 대부분이 여기였다. 아티스트 상세 페이지의 사진 피드, 아티스트 목록, 단체 페이지의 큰 이미지, 모든 페이지에 뜨는 프로필 아이콘 등 **방문자가 가장 많이 보는 화면들**이 아직 원본을 내보내고 있었다.

총 36곳을 연결했고, 각 화면에서 실제로 보이는 크기에 맞춰 지정했다(아이콘은 작게, 큰 사진은 크게).

### 작업 2. 화면 밖 사진은 스크롤해야 받도록 바꿨다 (23곳)

**왜 했나 —** 홈 화면 하나가 사진 185장을 참조하는데, 스크롤해서 보지도 않은 사진까지 미리 다 받고 있었다. 보는 것만 받으면 그만큼 줄어든다.

### 작업 3. 같은 문제가 다시 생기지 않도록 자동 검사를 넣었다

**왜 했나 —** 이 문제는 누가 코드를 잘못 써서 생긴 게 아니다. **주변 코드를 그대로 따라 쓰다가** 하나씩 쌓인 것이다. 그래서 사람이 검토하는 방식으로는 반복해서 놓친다. 실제로 이번에도 눈으로 훑었을 때 절반 넘게 빠뜨렸고, 자동 검사를 만들고 나서야 전부 찾았다.

이제 누군가 원본을 그대로 내보내는 코드를 새로 쓰면 **검사가 자동으로 실패하며 파일 이름을 알려준다.**

검사가 실제로 작동하는지도 확인했다 — 고친 것을 일부러 되돌려보고, 검사가 그 파일을 정확히 짚어 실패하는 것을 본 뒤 복구했다.

### 작업 4. 검색 로봇 규칙(robots.txt)을 추가했다

**왜 했나 —** 지금까지 이 규칙이 **아예 없었다.** 어떤 로봇이든 사이트 전체를 마음대로 긁어갈 수 있는 상태였다.

다만 전면 차단은 하지 않았다. 사이트가 검색 노출을 위한 설정을 갖추고 있어서, 다 막으면 **구글·네이버 검색에서도 사라진다.** 그래서 **검색엔진은 그대로 두고, 데이터 수집만 하는 AI 로봇만 차단**했다.

## 하지 않기로 한 것과 그 이유

작업만큼 중요한 부분이다.

### A. 저장된 원본 사진을 줄여서 교체하는 것 (2MB 넘는 30장)

**왜 안 했나 —** 세 가지 이유다.

1. **되돌릴 수 없다.** 원본을 덮어쓰면 사라진다
2. **아티스트가 올린 작품 사진이다.** 서비스가 임의로 화질을 낮추는 것이 맞는지는 기술이 아니라 동의의 문제다
3. **효과가 생각보다 작다.** 작업 1을 하고 나면 이용자가 받는 크기는 이미 23.7 KB로 같아진다. 원본을 줄여도 이용자 입장에서 달라지는 게 없다

**다음 달 실제 사용량을 보고 결정하는 것이 맞다.** 되돌릴 수 없는 작업을, 필요한지도 모르는 상태에서 먼저 할 이유가 없다.

### B. 사진의 캐시 설정을 바꾸는 것

**왜 안 했나 — 할 수 없어서다.**

사진마다 "이 사진은 오래 보관해도 된다"는 표시를 붙일 수 있는데, 우리 코드는 그 표시를 **정확하게 붙이고 있었다.** 그런데 Supabase가 그것을 무시하고 있었다.

테스트로 확인했다. 사진을 하나 새로 올리고 바로 확인해보니, 우리가 지정한 값이 아니라 Supabase가 정한 값이 붙어 있었다. Supabase 쪽에 같은 문제가 여러 번 보고돼 있고 아직 해결되지 않았다.

**우리 코드 문제가 아니었고, 우리가 고칠 수 있는 것도 아니었다.** 대신 작업 1의 축소 장치를 거치면 우리가 직접 표시를 붙일 수 있어서, 그 경로로 우회했다.

---

## 무엇을 확인했나

고쳤다고 말하기 전에 실제로 돌려봤다.

| 확인한 것 | 결과 |
|---|---|
| 자동 검사 전체 | 60개 통과 |
| 코드 오류 검사 | 0건 |
| 사이트 빌드 | 성공 |
| **실제 라이브 사진으로 축소 장치 시험** | 모든 크기에서 정상 |

특히 마지막이 중요했다. **깨질 뻔한 지점이 하나 있었다.**

축소 장치는 우리 사진 창고에 있는 사진만 처리하고, 인스타그램 사진이나 자동 생성 아바타는 거부한다. 만약 그런 사진까지 장치로 보냈다면 **화면에서 이미지가 통째로 안 떴을 것이다.** 실제로 확인해보니 거부가 맞았고, 우리 코드는 그런 사진을 장치로 보내지 않도록 돼 있었다. 이 동작을 테스트로 고정해서 앞으로도 깨지지 않게 했다.
